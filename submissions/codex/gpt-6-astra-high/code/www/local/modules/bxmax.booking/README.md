# bxmax.booking

Лендинг «Лак&Точка» и онлайн-запись для 1С-Битрикс. Документ-корень проекта — `www`. Нужны PHP 8.2+, модули main, iblock, sprint.migration, MySQL/MariaDB с InnoDB. Проверено на PHP 8.4 и main 26.750.0.

## Развёртывание

Из корня репозитория в окружении Omut:

```sh
bash .agents/skills/omut-env/scripts/omut-env.sh php www/bitrix/modules/sprint.migration/tools/migrate.php up Version20260922160000
```

На другом сервере используйте его PHP CLI с настроенными подключениями Битрикса. Миграция находится в `www/local/php_interface/migrations/`. Установщик создаёт таблицы, уникальные индексы, инфоблоки, 8 услуг, 3 мастера, 420 часовых слотов, почтовое событие, шаблон, агент, компонент и административные страницы. Идентификаторы контента вычисляются, не зашиты в код.

Альтернативный CLI-вход для установки без запуска миграции:

```sh
bash .agents/skills/omut-env/scripts/omut-env.sh php www/local/tools/booking-deploy.php
```

Не смешивайте ручную установку и управление состоянием миграции. Исходная главная сохраняется в `install/home-backup.php` при первой установке. Страница доступна по `/`.

## Администрирование

Меню «Сервисы → Лак&Точка»:

- `/local/admin/bxmax_booking_entries.php` — заявки, контакты, услуга, мастер, время согласия; удаление освобождает слот.
- `/local/admin/bxmax_booking_slots.php` — расписание, фильтры мастера/даты, закрытие и открытие слотов.
- `/bitrix/admin/settings.php?mid=bxmax.booking&lang=ru` — e-mail администратора и права групп.

Использованы CAdminList, CAdminFilter, CAdminSorting и штатные права модуля: D — нет доступа, R — чтение, W — управление. Изменения выполняются POST с проверкой sessid и W. Неавторизованный посетитель попадает на стандартную авторизацию.

Адрес уведомления первоначально берётся из настроек сайта. На этом стенде — `ai@example.com`; доставка подтверждена локальным Mailpit. На рабочем сервере настройте штатную почту Битрикса и реальный адрес получателя.

## Архитектура и данные

- Engine Controller → ServiceLocator → сервисы → репозитории → D7 ORM.
- `lib/Model` — точные контрактные таблицы `bxmax_booking_slot`, `bxmax_booking_entry`.
- `lib/Controller/Api` — тонкие публичные actions, GET для расписания, POST и CSRF для записи. Авторизация для публичной формы отключена, административные страницы защищены отдельно.
- `lib/Service/BookingService.php` — валидация, согласие, транзакция, постановка почтового события `BXMAX_BOOKING_NEW` в очередь.
- `lib/Repository/BookingRepository.php` — блокировка строки слота FOR UPDATE с целочисленным ID; уникальный индекс `ux_bxmax_entry_slot (SLOT_ID)` обеспечивает одну запись даже при обходе прикладной проверки. Закрытие слота использует ту же блокировку.
- `lib/Service/ScheduleService.php` — идемпотентные 14 дней, ежедневный агент. Исторические слоты сохраняются; интерфейс ограничивает выбор текущим горизонтом.
- `lib/Repository/CatalogRepository.php` — ORM инфоблоков, выбор только собственного типа, кеш чтения.
- `lib/Admin/Lists.php` — штатные списки и фильтры.
- `install/components/bxmax/booking` — исходник собственного компонента; установщик копирует его в `/local/components/bxmax/booking`.
- `views`, `assets` — самостоятельно написанные HTML, CSS, vanilla JS и локальные ассеты.

Время студии — Europe/Saratov, UTC+4. ORM хранит время в часовом поясе сервера; при фильтрации даты нормализуются к нему, при выдаче ISO-8601 — к времени студии. Согласие хранится как CONSENT_AT и версия текста CONSENT_VERSION. Дополнительное поле CLOSED закрывает слот независимо от заявки.

`slots.list` отдаёт только id, startsAt, endsAt, status. Клиент не получает имя, телефон или сведения о заявке. Перед отправкой проверяются услуга, мастер, существование слота, прошедшее время, занятость и согласие. При ошибках транзакции журнал PSR-3 не содержит контактов клиента.

## Проверки

```sh
python3 www/local/modules/bxmax.booking/tests/http-contract.py
bash .agents/skills/omut-env/scripts/omut-env.sh php www/local/modules/bxmax.booking/tests/verify.php
bash .agents/skills/omut-env/scripts/omut-env.sh php www/local/modules/bxmax.booking/tests/permissions.php
```

Тесты предназначены для этого демонстрационного стенда. HTTP-тест создаёт тестовую заявку; запускайте затем verify.php для удаления заявок с фиксированными тестовыми именами. Он также создаёт/удаляет собственные тестовые записи и проверяет закрытие слота. permissions.php создаёт временную группу и удаляет её в finally.

Проверено: отсутствие/ложное согласие; неизвестные ID; имя/телефон; CSRF; восемь независимых конкурентных сессий (один успех, семь SLOT_TAKEN); отсутствие персональных данных в расписании; ISO-время; 420 слотов и повторная генерация без дублей; DB UNIQUE; закрытие/открытие; удаление заявки; событие и доставка e-mail; права D/R/W и меню; рендер штатных административных таблиц.

В браузере: 360/768/1440, отсутствие горизонтального переполнения, мобильное меню, галерея, выбор услуги/мастера, недели, клавиатурные стрелки/Enter, отказ без согласия, отправка без перезагрузки, экран успеха. У полей есть label; день — tab, время — option с aria-selected/aria-disabled; сообщения — role=status. Уважён prefers-reduced-motion.

## Удаление и повторная установка

Удаление намеренно уничтожает данные модуля. Для рабочего сайта предварительно сохраните резервную копию. В рамках проверки на стенде полный цикл down/up выполнен успешно.

```sh
bash .agents/skills/omut-env/scripts/omut-env.sh php www/bitrix/modules/sprint.migration/tools/migrate.php down Version20260922160000
bash .agents/skills/omut-env/scripts/omut-env.sh php www/bitrix/modules/sprint.migration/tools/migrate.php up Version20260922160000
```

Удаляются собственные таблицы, тип инфоблоков вместе с контентом, агент, событие/шаблон/очередь уведомлений, опции, права, установленный компонент и локальные административные входы. Восстанавливается исходная главная. Исходники модуля и миграции остаются для повторной установки. Ядро `/bitrix/` не изменяется.

Референс и допущения — в корневом SOLUTION.md, фотографии и лицензии — в [assets/SOURCES.md](assets/SOURCES.md).
